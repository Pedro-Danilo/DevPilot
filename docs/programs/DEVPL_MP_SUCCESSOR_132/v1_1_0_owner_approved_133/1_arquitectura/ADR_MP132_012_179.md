# ADR-MP-132-012 — UI_FIRST_PILOT_B_V1

## Contexto
Pilot B es un único workspace continuo desde B0 hasta B7. La guía COR-178 capturaba identidad del proyecto antes de Project Entry; el Charter decía que el release arrancaría fuera de DevPilot. Esa ambigüedad confundía el origen de acciones de proyecto y la independencia del artefacto desplegado.

## Decisión Owner
El operador humano ejecuta todo el ciclo del proyecto desde controles UI normales, incluidas aprobaciones y Git/release. El backend puede ejecutar internamente Git, Python, build, jobs y deploy mediante herramientas tipadas, PathGuard, dry-run/preimages, autoridad, recibos y rollback. Ninguna terminal humana, editor externo, inyección de fixtures, DevTools o ChatGPT sirve para completar un paso del Pilot B. Se permite consola para levantar API/UI hasta que exista instalador, autorizar parent de instalación ya consentido y acotado, auditar y aplicar correctivos **a DevPilot**.

Identidad ID/nombre/root final y necesidad nacen exclusivamente en Project Entry. Parent de instalación no es target del proyecto; PathGuard deniega destinos fuera de parents autorizados. Auditoría toma snapshot antes, obtiene ID/root únicos del registro después de bootstrap UI, y comprueba conservación tras reinicio sin mutar el workspace.

El release/deploy/health/rollback del proyecto debe iniciarse en UI. La aplicación liberada debe poder ejecutarse independientemente de DevPilot. Que sea autónoma no autoriza desplegarla manualmente para satisfacer M6.

## Consecuencias y negativas
- Los gates M2–M6/M10 exigen recibos del mismo workspace y `operator_project_writes=0`, `normal_user_terminal_escapes=0`, `journey_actions_via_devpilot_ui=true`.
- No se autoriza MP-1B, red externa, provider global ni modelos por disponibilidad.
- No se altera ADR-011 ni recibos históricos; correcciones S2/S3 meramente visuales siguen OBSERVE_ONLY.
- R9 instala/arranca la plataforma; no sustituye la UX de Pilot B.
- COR-179 solo rectifica coordinación de COR-178; R02-06 no queda autorizado.

## Verificación
Auditor de B0 demuestra unicidad de alta en registry desde pre-snapshot, root bajo parent explícito, YAML/registration/engineering state/Git neutral; reboot conserva identidad y Home/Status concuerdan. R5 y R6 verifican acciones UI de Git/release con receipts, nunca CLI humano.
